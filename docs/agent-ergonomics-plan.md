номера строк проверены 2026-09-14 на коммите `050e46d0` репозитория ANG.

## 0. Контекст, который нельзя выяснить из кода

### 0.1 Что такое ANG и где что лежит

- Репозиторий генератора: `~/Desktop/work/ang`. Go-модуль. CLI — `cmd/ang/*.go`,
  компилятор — `compiler/`, шаблоны — `templates/`. 241 файл `_test.go`,
  фикстуры в `cmd/ang/testdata`.
- Эталонный проект-потребитель: `~/Desktop/work/deal/dealingi-back`. Это **единственный
  боевой проект** на ANG; любое изменение генератора проверяется на нём.
- Проект пиннит ревизию генератора файлом `ang.lock`:
  ```
  repository=https://github.com/strogmv/ang.git
  commit=050e46d0fe4536bb10be54e33604e449012ce642
  ```
  `make generate` в проекте (Makefile, цели `verify-ang` → `build-ang` → `generate`)
  проверяет, что checkout `../../ang` стоит ровно на этом коммите и чист, собирает
  `bin/ang` и запускает `bin/ang build`. `make sdk` делает то же с флагом
  `--frontend-app-dir ../dealingi-front/src/@sdk`.
- CI проекта (`.github/workflows/ci.yml`, джоба `generated-output`) клонирует ANG на
  коммит из `ang.lock`, запускает генерацию и требует `git diff --exit-code` и
  отсутствие untracked-файлов. **На коммите `050e46d0` эта джоба зелёная.** Это
  базовая линия: после твоих изменений она обязана остаться зелёной, пока
  `ang.lock` не обновят намеренно.

### 0.2 Как устроена сборка сейчас (`cmd/ang/build_transaction.go`)

Прочитай этот файл целиком перед P0. Кратко:

1. `generatedTransactionPaths()` (строка 451) — **фиксированный список каталогов**,
   которыми «владеет» транзакция: `cmd/server`, `internal`, `api`, `db`, `deploy`,
   `sdk`, `scripts`, `tests`, `.ang/cache`, `.env.example`, `ang-manifest.json`,
   `atlas.hcl`, `sqlc.yaml` плюс backend/frontend-каталоги целей.
2. `beginBuildTransaction()` (31) — для каждого такого пути делает снимок в
   `.ang-build-transaction-*/stage`.
3. `CreateWorkspace()` (124) — создаёт `.ang-build-workspace-*/project`, где всё
   верхнеуровневое — символические ссылки на настоящий проект, а «принадлежащие»
   пути материализованы копией.
4. Генерация и `go build` идут в workspace.
5. `CaptureWorkspace()` (240) — копирует принадлежащие пути из workspace в `stage`.
6. `Commit()` (62) — для каждого пути: `os.Rename(path → backup)`, затем
   `os.Rename(stage → path)`.

Следствие, которое и есть главная проблема: **каталог заменяется целиком снимком,
сделанным в начале сборки.** Всё, что человек или агент записал в `internal/`,
`db/`, `deploy/`, `tests/`, `scripts/` за время сборки (минуты), исчезает при
`Commit`. Это не «копирование проекта», это подмена каталогов по гранулярности
«каталог», а не «файл».

Насколько это широко в эталонном проекте (посчитано `git ls-files`):

| каталог | файлов | с маркером генерации (`.gen.go`, `/gen/`) |
|---|---|---|
| `internal` | 1652 | 865 |
| `db` | 167 | 0 |
| `deploy` | 86 | 0 |
| `tests` | 214 | 0 |
| `scripts` | 12 | 0 |

`db/migrations/*.sql`, `deploy/prod/*.yaml`, `tests/e2e/*.test.ts` — ручные файлы,
и они живут внутри каталогов, которые сборка подменяет целиком. Отсутствие маркера
не значит «ручной» (например, `internal/transport/http/common.go` генерируется без
суффикса), поэтому **владение нужно вести по списку файлов, а не по каталогам**.

### 0.3 Копирование SDK во фронт (`cmd/ang/build_helpers.go:368`)

`copyFrontendSDK(srcDir, appDir)`:
- вызывает `ensureSDKTarget(appDir)` (`cmd/ang/sdk_target_guard.go`) — отказывается,
  если в каталоге есть маркеры проекта (`.git`, `package.json`, `src`,
  `node_modules`, `go.mod`, `cue`) или он не пуст и без `sdk-manifest.json`;
- затем `os.RemoveAll(appDir)` и запись файлов по одному.

Защита появилась после того, как флаг, направленный на корень фронта, трижды удалял
`src/.git`. Защита хорошая, оставшаяся дыра — **удалить-потом-записать**: если
запись упадёт посередине, SDK во фронте нет, а откатывать нечего.

### 0.4 Что уже есть и что не надо изобретать заново

- `ang build --dry-run` (`cmd/ang/dry_run.go`, вызовы в `build.go:120–134`) —
  генерирует во временный корень и пишет манифест: для каждого файла
  `create | update | unchanged`. **Содержимого изменений в манифесте нет.**
  MCP-инструмент `ang_dry_run` (`internal/mcp/tools_core.go:189`) возвращает этот
  манифест.
- `ang build --target <name|lang|stack>` (`build_helpers.go:60`) — сборка только
  выбранных целей. Это гранулярность «цель», не «сервис».
- `ang vet logic` — «Audit embedded Go snippets for syntax errors» (`main.go:149`,
  диспетчер `case "vet"` → `runVet`, `main.go:64`). Парсит синтаксис. **`go/types`
  в репозитории не используется нигде** — проверки типов до полной сборки нет.
- `ang fmt` — канонический формат CUE и нормализация алиасов flow.
- `cmd/ang/template_hash.go`, `.ang/cache` — хеширование шаблонов и кэш; смотри,
  прежде чем делать инкрементальную сборку (P2.2).
- `cmd/ang/artifact_manifest.go` — запись артефактов сборки. Если сборка уже
  фиксирует каждый созданный файл, **это источник правды для владения в P0.1**;
  если нет — сделай его таким.
- Выход форматируется: `compiler/templateset/emit.go:96` — `imports.Process`,
  `compiler/emitter/*.go` — `format.Source`. Значит, беспорядок из п. 3 живёт только
  в CUE-исходниках, не в результате.

## P0. Сборка не трогает ничего, кроме своих файлов

### P0.1 Владение по списку файлов, не по каталогам

> **Реализовано 2026-09-14, ветка `agent-ergonomics-p0` — другим способом, чем
> описано ниже.** Список эмитированных файлов собрать надёжно нельзя: записи
> разбросаны по 49 вызовам в 30 файлах, центрального писателя нет, и любой
> пропущенный путь стал бы новой дырой. Вместо этого `Commit()` делает
> **трёхстороннее слияние по файлам** (`cmd/ang/build_transaction.go`, комментарий
> к `buildTransactionEntry`):
>
> - `base` — снимок пути на старте транзакции, `stage` — результат генерации,
>   `path` — проект в момент коммита;
> - файл, который генератор не менял (`stage == base`), не трогается вообще —
>   любые правки, созданные и удалённые во время сборки файлы сохраняются;
> - изменённый генератором файл публикуется rename-ом; если его же изменили в
>   проекте, версия проекта сначала копируется в `.ang/conflicts/<время>/`, путь
>   печатается в предупреждении;
> - удаляются только файлы, удалённые генератором и не тронутые в проекте; пустые
>   каталоги убираются, только если существовали на старте и их нет в `stage`;
> - откат при ошибке — по журналу выполненных rename.
>
> `stage` для путей вне рабочей копии заполняется лениво, поэтому копирований не
> больше, чем раньше, а при коммите трогаются только реально изменённые файлы.
> Секция `generated_files` в `ang-manifest.json` **не нужна и не добавлена**;
> выход генератора не изменился. Удаление устаревших сгенерированных файлов
> работает ровно как до изменения (раньше это делала подмена каталога снимком,
> теперь — слияние), новой логики очистки не появилось.
>
> Тесты: `TestBuildTransactionCommit*`, `TestBuildTransactionEntryNeverStagedIsLeftAlone`,
> интеграционный `TestRunBuildKeepsFilesWrittenDuringBuild` (через тестовую точку
> `buildBeforeCommitHook`). Описание ниже оставлено как исходная постановка.

**Проблема.** См. 0.2. `Commit()` подменяет `db/`, `deploy/`, `tests/`, `scripts/`,
`internal/` целиком.

**Требуемое поведение.**
- Сборка знает точный список файлов, которые она создала в прошлый раз, и точный
  список, который создаёт сейчас. Она пишет **только** эти файлы. Удаляет только те,
  что были в прошлом списке и отсутствуют в новом.
- Любой файл в «принадлежащем» каталоге, которого нет в списке, сборка не читает,
  не копирует, не удаляет и не переименовывает. Ручной `db/migrations/x.sql`,
  записанный во время сборки, после `Commit` на месте, байт в байт.
- Список хранится в проекте в детерминированном виде (отсортирован, относительные
  пути с `/`), например в `ang-manifest.json` — если `artifact_manifest.go` уже
  пишет туда список файлов, расширь его; если нет, добавь секцию
  `"generated_files": [...]`. Файл сам входит в список.
- Первый запуск на проекте без списка: сборка должна работать как раньше **один
  раз**, чтобы создать список, и печатать предупреждение. Не ломай миграцию
  существующего проекта.

**Шаги.**
1. Найди, где известен набор эмитируемых файлов (эмиттеры в `compiler/`,
   `templateset/emit.go`; собери путь каждого записанного файла в один срез).
2. Замени модель транзакции: вместо `entries` по каталогам — `entries` по файлам.
   `Commit` делает `rename(stage/file → file)` для каждого файла; удаление — для
   разности старого и нового списка. Родительские каталоги создаются, пустые
   каталоги после удаления убираются, непустые — нет.
3. `CreateWorkspace` остаётся overlay-ом на символических ссылках, но
   материализует только файлы из объединения старого и нового списка.
4. Сохрани атомарность на уровне файла (rename), а откат — по журналу выполненных
   rename, как сейчас в `restoreCommitted`.

**Приёмка.**
- Тест в `cmd/ang`: создать проект-фикстуру, запустить сборку, во время сборки
  (через хук/канал в тесте) записать `db/migrations/manual.sql`,
  `tests/e2e/manual.test.ts`, `internal/service/manual_note.go`; после сборки все
  три на месте с исходным содержимым.
- Тест: удалить из CUE один эндпоинт, собрать — файлы, которые перестали
  эмитироваться, удалены; никакие другие файлы не тронуты (сравнение дерева до/после
  по списку).
- В `dealingi-back` на ветке с твоими изменениями: `make generate` → `git status`
  показывает изменения **только** в `ang-manifest.json` (новая секция). Затем
  `make generate` второй раз → `git status` чист.

**Запреты.** Не меняй список каталогов в `generatedTransactionPaths` «на глаз» —
замени сам принцип. Не добавляй эвристику по суффиксу `.gen.go`: см. 0.2, она
неверна.

### P0.2 Копирование SDK во фронт — атомарно

> **Закрыто P0.1, отдельного кода не потребовалось (2026-09-14).**
> `copyFrontendSDK` вызывается только шагом сборки (`step_registry.go`), а
> `build.go` заранее подменяет `--frontend-app-dir` на stage транзакции
> (`targetOutput.FrontendAppDir = stagePath(...)`). `RemoveAll` и запись идут в
> stage; реальный каталог SDK меняется только в `Commit` — пофайловым слиянием с
> откатом. Копирование, упавшее посередине, роняет сборку, транзакция
> откатывается, SDK приложения не тронут. Доказано тестами
> `TestFrontendSDKCopyFailureDuringBuildLeavesAppSDKUntouched` и
> `TestFrontendSDKCopyPublishesThroughMerge`. Если `copyFrontendSDK` когда-нибудь
> позовут вне сборки, этот пункт снова актуален.

**Проблема.** См. 0.3: `RemoveAll` перед записью.

**Требуемое поведение.**
- SDK собирается в соседний временный каталог `<appDir>.ang-stage-*` на той же
  файловой системе, затем `rename(appDir → appDir.ang-backup-*)`,
  `rename(stage → appDir)`, удаление backup. При ошибке — обратный rename.
- `sdk-manifest.json` пишется **всегда** и первым, чтобы `ensureSDKTarget`
  в следующий раз имел положительное доказательство.
- `ensureSDKTarget` не трогать; его тесты (`sdk_target_guard_test.go`) должны
  остаться зелёными.

**Приёмка.** Тест: сымитировать ошибку записи на середине копирования (например,
файл с недопустимым именем во входном наборе) — целевой каталог остался в прежнем
состоянии, backup удалён, ошибка возвращена.

### P0.3 Бинарник сам проверяет `ang.lock`

> **Реализовано 2026-09-14** (`cmd/ang/ang_lock.go`). ldflags не понадобились: Go
> сам вшивает `vcs.revision` и `vcs.modified` (`debug.ReadBuildInfo`). `ang build`
> — во всех фазах, включая `plan`/`apply` и dry-run — сверяет ревизию с `commit=`
> из `ang.lock` до генерации. Расхождение — `ANG_LOCK_MISMATCH` (`docs/error_codes.md`,
> подсказка в `ang doctor`), обход — `--allow-lock-mismatch` (пробрасывается и в
> dry-run-подпроцесс `template diff`). Нет VCS-информации или бинарник собран с
> незакоммиченными правками — только предупреждение в stderr. `ang version`
> печатает ревизию.
>
> Проверено на dealingi-back: бинарник `f2194fae` без флага отказал с кодом 1, не
> начав генерацию; с флагом dry-run прошёл — **2094 файла, 0 новых, 0 изменённых**.
>
> **Ограничение:** проверка есть только в бинарниках, собранных после этого
> изменения. На 2026-09-14 `dealingi-back/bin/ang` собран из `0bb3b928`, а
> `~/go/bin/ang` — из `09a4efaf` с грязным деревом; оба старше пина и проверку не
> содержат. Пока их не пересобрать, прямой запуск по-прежнему опасен.

**Проблема.** Проверку ревизии делает Makefile проекта (`verify-ang`). Запуск
`ang build` напрямую, из другого каталога или глобального `~/go/bin/ang`, эту
проверку обходит — и генерирует другой контракт.

**Требуемое поведение.**
- Коммит и «грязность» дерева вшиваются в бинарник через `-ldflags -X` при
  сборке (`Makefile` в ANG и `build-ang` в проекте передают
  `git rev-parse HEAD` и `git status --porcelain`).
- `ang build` при наличии `ang.lock` в корне проекта сравнивает `commit=` с
  вшитым. Не совпало — ошибка с кодом диагностики и текстом «expected X, running Y,
  run: git -C <ANG_SRC> checkout X»; собрать можно только с явным
  `--allow-lock-mismatch`. Бинарник без вшитого коммита (сборка `go run`) — только
  предупреждение.
- `ang --version` печатает коммит.

**Приёмка.** Тест на функцию сравнения; ручная проверка: в `dealingi-back`
запустить `~/go/bin/ang build --dry-run` (старый бинарник от 29 августа) — должен
отказать.

## P0.4 Брошенные рабочие каталоги сборки

> **Реализовано 2026-09-14** (`cmd/ang/build_scratch_sweep.go`,
> `process_alive_unix.go`, `process_alive_windows.go`). Живость — сигнал 0 на unix
> (`EPERM` тоже значит «жив»); на windows надёжной проверки нет, и владелец всегда
> считается живым — лучше оставить мусор, чем удалить идущую сборку. Уборка —
> best effort и никогда не роняет сборку; итог печатается в логе сборки, каталоги
> с `keep` — отдельным предупреждением. Тесты: `TestSweepAbandonedBuildScratch`,
> `TestBuildTransactionRecordsOwnerAndSweepsAbandonedScratch`.
>
> **На dealingi-back не запускалось сознательно:** первая сборка новым бинарником
> удалит все 17 старых каталогов (657 МБ, все старше суток, без `owner.json`).
> Это решение владельца проекта.

**Проблема.** Сборка, убитая сигналом или упавшая до `Rollback`, не удаляет свои
`.ang-build-transaction-*` (рядом с принадлежащими путями) и
`.ang-build-workspace-*` (рядом с корнем проекта). `.gitignore` их скрывает, и они
копятся. В dealingi-back на 2026-09-14: 13 транзакций и 4 рабочие копии,
**657 МБ**, самая старая — 2026-08-09; каждая копия содержит снимок `tests/`
(91 МБ, там `node_modules`).

**Требуемое поведение.**
- При создании рабочего каталога пиши в него `owner.json`: PID, имя хоста, время.
- В начале сборки находи каталоги со своими префиксами в тех же местах и удаляй
  те, чей владелец мёртв: хост совпадает, а процесса с этим PID нет. Каталоги без
  `owner.json` (старый формат) удаляй, только если они старше 24 часов.
- Никогда не трогай каталог живого процесса и каталог с другого хоста.
- Сообщай одной строкой, сколько удалено и сколько места освобождено.
- Каталоги, оставленные `keepWorkDirs` после неудачного отката (там оригиналы),
  **не удалять автоматически** — пометь их в `owner.json` и напечатай путь.

**Приёмка.** Тест: каталог с PID несуществующего процесса удаляется; с PID
текущего процесса — нет; без `owner.json` младше 24 часов — нет; с флагом
`keep` — нет.

## P1. Генерация воспроизводима, и это проверяется одной командой

> **Сужено и реализовано 2026-09-14.** Проверка воспроизводимости в CI ANG
> **уже есть** — план ошибочно предлагал её добавить: `.github/workflows/ci.yml`,
> джоба `determinism-matrix` (ubuntu/macos/windows, `scripts/determinism_ci`:

проекта. У генератора нет собственной проверки, а история проекта помнит случаи,
когда `make generate` не воспроизводил закоммиченный код и менял контракт API.

**Требуемое поведение.**
- `ang build --check`: генерация во временный корень (можно поверх механизма
  `--dry-run`), сравнение с текущими файлами по списку из P0.1, вывод отличий
  (пути, `+`/`-`/`~`), код выхода 1 при любом отличии, 0 — при полном совпадении.
  Ничего в проект не пишет.
- Детерминизм: любой обход `map` в эмиттерах и шаблонах перед выводом сортируется;
  в выходе нет времени сборки, случайных идентификаторов, абсолютных путей машины.
- В CI самого ANG: джоба берёт фикстуру (минимальный проект в `cmd/ang/testdata`
  или `examples/`), собирает дважды в два каталога и сравнивает деревья байт в байт.

**Шаги.**
1. Реализуй `--check` как режим поверх `--dry-run`: после генерации во временный
   корень — сравнение, отчёт, код выхода.
2. Найди источники недетерминизма: `grep -rn 'range .*map\|for .* := range' compiler
   templates` и точки, где вывод формируется из `map` без `sort`. Исправляй по факту,
   не переписывай обход всех циклов вслепую.
3. Добавь CI-джобу.

**Приёмка.** `cd dealingi-back && make generate && bin/ang build --check` → код 0.
Джоба ANG зелёная.

## P2. Короткий цикл: увидеть изменение до записи, пересобирать только нужное

### P2.1 `--dry-run` показывает содержимое, а не только имена

> **Реализовано 2026-09-14.** `ang build --dry-run --diff` печатает unified diff
> (`github.com/pmezard/go-difflib`, 3 строки контекста; новые файлы — от
> `/dev/null`; бинарные — одной строкой) вместо JSON-манифеста. `--diff-out <dir>`
> пишет `<dir>/<путь>.patch`. С `--check` — сначала список расхождений, затем
> диффы, всё в stderr. Оба флага требуют `--dry-run` или `--check`. MCP
> `ang_dry_run` принимает `diff: bool` и возвращает поле `diffs` (патч до 200 КБ,
> всего до 2 МБ, остальное — списком без содержимого). Удалённые файлы не
> показываются — то же ограничение, что у `--check`.
>
> Проверено на dealingi-back: ручная правка в `auth__register_user.gen.go` дала
> ровно один патч, откатывающий её; JSON-манифест при `--diff` не печатается.

**Проблема.** Манифест `dry_run.go` говорит «update», но не говорит что. Агент не
может оценить правку CUE, не записав результат в проект.

**Требуемое поведение.**
- `ang build --dry-run --diff` печатает unified diff (формат `git diff --no-index`)
  для каждого файла со статусом `update`; для `create` — весь файл как добавленный;
  для удаляемых — как удалённый. Порядок файлов отсортирован.
- `--diff-out <dir>` пишет то же в `<dir>/<путь>.patch` вместо stdout.
- MCP `ang_dry_run` получает параметр `diff: bool`, возвращает диффы в ответе
  (ограничь размер, например 200 КБ на файл, остальное — «truncated, see
  --diff-out»).

**Приёмка.** Тест: фикстура, изменение одной строки в CUE, `--dry-run --diff`
содержит ровно один hunk с этой строкой.

### P2.2 Инкрементальная сборка

> **Сначала сделано ускорение, а не кеш (2026-09-15).** Профиль dry run на
> dealingi-back: из ~41 с 34 с уходило на `imports.Process` в эмиттере
> `Service Impls` (было 42 с на полной сборке). Причина: шаблоны методов не
> импортируют пакеты, которые используют тела из CUE (`strconv`,
> `crypto/sha256`, `internal/pkg/*`). goimports ищет их, **для каждого файла
> заново** разбирая все `.go` в каталоге юнита (740 файлов `internal/service`),
> а иногда ещё и обходя модули, — O(n²). Юнит передаётся относительным путём,
> то есть каталог — это старые файлы проекта на диске.
>
> `compiler/emitter/go_format.go`: `withPreviousImports` берёт из прошлого
> вывода того же юнита импорты, покрывающие неразрешённые ссылки, и добавляет их
> так же, как это делает сам goimports (удалить неиспользуемые, добавить по
> порядку путей через `astutil`). goimports тогда заканчивает на первом проходе.
> Если прошлого файла нет или он покрывает не всё — прежний полный путь.
> Проверено: все 1117 вызовов форматтера байт-в-байт совпали с прежним выводом,
> `Service Impls` 42 с → 5 с, `--check` 2094/2094, `go test ./...` зелёный.
> Зависимость от прошлого вывода не новая: goimports и раньше выбирал импорты по
> старым соседним файлам. Известный край: если соседний файл объявит глобальную
> переменную с именем пакета, который прошлый вывод импортировал, быстрый путь
> оставит импорт, а полный — нет; такое ловит `go verify`.
>
> Хеш-кеш ниже **не делался**: при сборке в ~11 с (`--check`) выигрыш мал, а
> `BuildFingerprint` не включает ревизию компилятора, и `inputHash` покрывает
> только CUE (не `ang.yaml`, `go.mod`, шаблоны проекта, `ANG_*`), так что кеш по
> описанию ниже был бы небезопасен. Возвращаться к нему — только расширив хеш.

**Проблема.** Любая правка — полная генерация всех целей. На эталонном проекте это
минуты.

**Требуемое поведение.**
- Сборка хеширует входы каждого эмитируемого файла (CUE-фрагменты и шаблоны, от
  которых он зависит) и хранит хеши в `.ang/cache` (каталог уже существует —
  см. `template_hash.go`). Файлы с неизменившимися входами не перегенерируются и не
  переписываются.
- Семантика результата **не меняется**: инкрементальная сборка обязана давать
  байт-в-байт тот же результат, что полная. `--no-cache` принудительно делает
  полную.
- Это важнее, чем «пересобрать один сервис»: сквозные файлы (маршруты,
  `common.go`, индекс SDK) зависят от всех сервисов, и любая «частичная» сборка по
  именам сервисов либо забудет их, либо сведётся к тому же графу зависимостей.
  Не делай флаг `--only service=`.

**Приёмка.** Тест: полная сборка, затем правка одного `impl_*.cue`, инкрементальная
сборка — переписаны только файлы этого сервиса и сквозные; результат совпадает с
результатом полной сборки после той же правки (сравнение деревьев).

## P3. Go внутри CUE: форматирование и проверка типов без полной сборки

### P3.1 `ang fmt` форматирует встроенный Go

> **Реализовано 2026-09-15** (`cmd/ang/fmt_embedded_go.go`,
> `fmt_embedded_go_decode.go`). Поля: `func` (выражение), `code` (операторы) и
> определения `#…`, если в них литерал функции; `sql` и прочие строки не
> трогаются. Форматируется только поле, значение которого — одна многострочная
> строка (конкатенация `""" + #Block + """` — не Go сама по себе). Интерполяции
> `\(…)` на время gofmt заменяются идентификаторами той же длины.
>
> Две вещи, которых план не предвидел:
> - **Сгенерированный код ссылается на строки CUE** (`// Source: file.cue:N`,
>   3071 раз в dealingi-back). Поэтому фрагмент, у которого gofmt поменял бы
>   число строк (раскрыть `if err != nil { return out, err }`), не трогается;
>   такие пропуски печатаются одной сводной строкой, поштучно — в `--json`.
> - **gofmt видит исходный текст CUE, где `\"` и `\\` ещё экранирование.** Результат
>   принимается, только если декодированный (`literal.Unquote`) Go до и после
>   совпадает токен в токен; иначе фрагмент пропускается с предупреждением.
>
> `--go-only`: только встроенный Go, без переименования действий и `cue fmt`.
> Нужен для проектов, чей CUE не в раскладке `cue fmt`: на dealingi-back
> `cue fmt` сам по себе меняет 589 из 646 файлов (у 24 — число строк). Без `cue`
> в PATH `ang fmt` раньше падал; теперь то же форматирование выполняется
> библиотекой (`cue fmt` = `parser.ParseFile` + `format.Node`).
>
> **Приёмка на копии dealingi-back:** `ang fmt --go-only` отформатировал 65
> фрагментов в 52 файлах, 238 оставил ради числа строк, 5 не разбираются до
> декодирования экранирования; повторный запуск ничего не меняет. `build --check`
> после этого: 306 файлов отличаются, и **все 626 изменённых строк — провенанс**
> (`// InputHash:`, `sha:` исходных `.cue`, `x-ang-input-hash`), ни одной строки
> кода. Критерий «форматирование входа не меняет выход» в буквальном виде
> недостижим для любой правки байтов CUE — хеши входа меняются всегда; проверяемый
> критерий: пересборка отличается только строками провенанса.

**Требуемое поведение.**
- `ang fmt` находит строковые литералы `"""…"""` в полях, которые генератор трактует
  как Go (ключ `code`, определения `#…Func`, значения `expr`/`value` действий
  `math.Expr`, `logic.Check` и т. п. — точный список возьми из
  `cmd/ang/actions.go` и `compiler/impl_sidecar.go`), и прогоняет их через
  `go/format`. Фрагмент, который не парсится как выражение/оператор/функция,
  оставляется как есть — с предупреждением, не ошибкой.
- Отступ фрагмента внутри CUE сохраняется; сама структура CUE не меняется.
- Однострочные `"…"` не трогать: их нельзя переформатировать без изменения
  семантики строки.

**Приёмка.** Тест: файл с фрагментом без отступов → после `ang fmt` отформатирован,
повторный `ang fmt` ничего не меняет. На `dealingi-back`: `ang fmt` → сборка →
`bin/ang build --check` даёт 0 (форматирование входа не меняет выход).

### P3.2 `ang vet logic --types`: проверка типов за секунды

> **Реализовано 2026-09-15** (`cmd/ang/vet_logic_types.go`). Иначе, чем
> описано ниже, — проще и без копии проекта:
> - генерация — обычный dry run в процессе (вывод и предупреждения глотаются,
>   показываются только при провале);
> - компиляция — `go build -overlay` по сгенерированным `.go` из dry run: проект
>   на диске не трогается, неизменённые пакеты берутся из кэша сборки. Пакеты —
>   `--packages`, по умолчанию `./internal/service/...`. «Один сервис» отдельно не
>   собрать: в dealingi-back все 17 сервисов — один пакет `service`;
> - привязка к CUE — **без карты строк**: в файлах методов её нет (есть только
>   заголовок со списком `.cue`), а встроенный Go копируется почти дословно.
>   Строка ищется по тексту с оценкой по трём соседним строкам с каждой стороны:
>   сначала в `.cue` из заголовка, потом по всему дереву CUE; колонка пересчитывается
>   по отступу. Нет однозначного совпадения (ошибка в каркасе, текст изменён
>   экранированием CUE) — печатается сгенерированное место и `.cue`, из которых
>   файл сделан.
>
> Попутно: старое `mapGoBuildErrorsToCUESource` в go verify ищет комментарий
> `// Generated from:`, которого текущие заголовки не пишут, — оно не срабатывает;
> не трогал.
>
> **Приёмка на копии dealingi-back:** в `impl_tender_get.cue` вызов
> `s.TenderProductRepo.ListByTender` заменён на несуществующий `ListByTenderNope` →
> `cue/api/impl_tender_get.cue:46:41: … has no field or method ListByTenderNope`
> (совпадение exact) + `generated: internal/service/tender__get_tender.gen.go:71:37`,
> 10.4 с (генерация 9.5, компиляция 0.8). Первый прогон после смены пакета
> компилирует ~6 с, дальше кэш. Цель ≤ 10 с — на границе; остаток — генерация
> всего проекта (P2.2 уже сократил её с ~41 до ~10 с).

**Проблема.** `vet logic` ловит только синтаксис. Неверное имя поля, неверная
сигнатура `(int64, error)` у finder-а, лишний аргумент — всё это всплывает только
после полной генерации и `go build`.

**Требуемое поведение.**
- Режим `--types`: для каждого сервиса генератор собирает **только** пакет этого
  сервиса и его прямые зависимости (порты, домен, DTO) во временный каталог поверх
  overlay-workspace из P0, и запускает на нём `go/types` (`golang.org/x/tools/go/packages`
  с `NeedTypes`) или, если это проще внедрить, `go vet ./internal/service/<pkg>/...`
  в workspace. Полная генерация всех целей, фронта, тестов и `go build ./...` не
  выполняется.
- Диагностика привязывается обратно к CUE: `cue/api/impl_x.cue:LINE:COL` фрагмента,
  а не к сгенерированному файлу. Для этого эмиттер должен сохранять карту
  «сгенерированная строка → файл/строка CUE» (посмотри, есть ли уже что-то похожее в
  `compiler/emitter/service_flow_codegen_ast_helpers.go`).
- Цель по времени на эталонном проекте: секунды на один сервис, не минуты.

**Приёмка.** Тест: фрагмент вызывает несуществующий метод репозитория → `vet logic
--types` печатает ошибку с координатами в `.cue`. На `dealingi-back`: время
`ang vet logic --types` для одного сервиса ≤ 10 с.

## P5. Чтобы агент работал с ANG с удовольствием, а не через силу

### P5.0 Факты, которых не видно из кода (проверены 2026-09-15)

**Сколько Go живёт внутри CUE в dealingi-back.** 27 823 строки Go в
`"""…"""`-строках: 477 блоков `func:` (литералы `logic.Call`), 27 блоков `code:`
(тела методов `impls: go`), 63 определения `#…Func` и 51 другое `#…`-определение с

собирается интерполяцией `\(#ИмяFunc)(…)` — это макросы, подставляемые *текстом*.

  `logic.Call` с `funcRef` (литерал функции — `resolveLogicCallSidecars`, импорты
  через `_funcRefImports`, потребляются в `emitter/service.go:555`). В dealingi-back
  **0 использований**. Sidecar-файл там — просто текст: он не обязан компилироваться,

- Эмиттер сервисов удаляет в `internal/service` только файлы с префиксом

  `Code generated by ANG`/`DO NOT EDIT` (`service.go:676`,
  `prune_generated.go:27`). Рукописный `tender__products.go` он не тронет.
- Рабочий каталог сборки — overlay проекта; `go verify` компилирует в нём и

- Хеш входа: `ComputeProjectHashWithRoot` (`compiler/pipeline.go:25`) — sha256 всех

### P5.1 Рукописный Go рядом с генератом — главное

**Проблема.** Всё из первого абзаца P5.0: Go пишется вслепую в строке, без gopls,
без gofmt (P3.1 форматирует только часть), с `\"` на каждой строке, с макросами
через интерполяцию, с тестами, которые можно написать только на весь метод.

**Целевая форма.** Реализации — обычные **методы на сгенерированном типе** в
рукописных файлах того же пакета:

```go
// internal/service/tender_products.go — рукописный, не .gen.go
package service

func (s *TenderImpl) listTenderProducts(ctx context.Context, tenderID string) ([]port.GetTenderResponseProductsItem, error) {
	if strings.TrimSpace(tenderID) == "" || s.TenderProductRepo == nil {
		return nil, nil
	}
	…
}
```

а в CUE остаётся вызов, который генератор *уже* умеет:

```cue
{ action: "logic.Call", func: "s.listTenderProducts", args: ["ctx", "req.TenderID"], output: "products" }
```

Почему методы, а не функции с параметром `s`: 343 из 427 литералов обращаются к `s`,
у типа `<Service>Impl` (например `TenderImpl`, см.
`func (s *TenderImpl) GetTender(…)` в генерате) есть неэкспортированные поля, и
метод в том же пакете — единственный способ видеть их без генерации интерфейсов.
gopls, `go build`, `go test`, трассировки — всё работает само, без директив и без
сопоставления текста. `\"` исчезает, потому что это больше не строка.

**Что нужно от ANG (маленькая часть).**
1. Правило именования и защита: рукописные файлы в каталогах генерата — любые
   `.go` **без** суффикса `.gen.go` и без шапки `Code generated by ANG`. Эмиттер и
   так их не удаляет (P5.0); добавь явный тест на это в `prune_generated_test.go`
   и явный пункт в `docs/commands.md`. Рукописные методы на типах `<Service>Impl`
   должны быть неэкспортированными; если в рукописном файле объявлен
   экспортированный метод на этом типе или метод с именем операции из CUE —
   диагностика `E_HAND_METHOD_SHADOWS_OPERATION` (в `emitter/service.go` после
   рендера, по `go/parser` рукописных файлов каталога).
2. `ang build --check` и dry-run не должны считать рукописные файлы «лишними» —
   сейчас так и есть (манифест перечисляет только сгенерированные), закрепи тестом.
3. Для блоков `impls: go: code` ничего нового не нужно:
   `code: "return s.getTenderImpl(ctx, req)"` — одна строка, метод рядом.
   `CleanImplCode` пропустит её как есть; проверь тестом.

**Что нужно от ANG (большая часть) — инструмент миграции `ang migrate go-blocks`.**
Он должен работать с **сгенерированным** кодом как с источником истины, потому что
это настоящий, компилирующийся Go, а CUE-текст — нет (интерполяции, экранирование).
Порядок:
1. Сборка проекта (обычная). Загрузить пакет `internal/service` через
   `golang.org/x/tools/go/packages` с `NeedTypes|NeedTypesInfo|NeedSyntax`.
2. **Сначала макросы.** Для каждого определения `#…` со строкой-литералом функции
   (63 `#…Func` + те из 51 прочих, что являются `(func(…){…})`): найти его
   *развёрнутый* текст в генерате (по любому месту использования), сделать из него
   рукописную функцию. Если тело обращается к `s.` — метод на `<Service>Impl`; если
   макрос при этом используется из нескольких сервисов — **не мигрировать, вывести
   в отчёт** (нужен интерфейс, это ручная работа). Иначе — функция уровня пакета в
   `internal/service/helpers_<имя>.go`. В CUE заменить `\(#XFunc)(` на `xFunc(` /
   `s.xFunc(` *внутри* строк (`cue/ast` + `cue/format`, как в
   `cmd/ang/template_merge.go`; не regex по файлу — иначе испортишь соседние строки),
   определение удалить. Пересобрать, `go build`, `go test`. Выход при этом
   **меняется** (на месте подставленного тела — вызов), поэтому критерий не
   «`--check` чист», а приёмка ниже: в диффе генерата только замена тела вызовом,
   тесты зелёные, повторный `--check` после миграции чист.
3. **Потом литералы `logic.Call`.** Для каждого шага с `func: """…"""`: найти в
   AST сгенерированного метода выражение `(func(…){…})(args)` (после P5.2 — по
   директиве `//line`; до неё — по `FlowStep.Line` и совпадению текста первой
   строки), взять `*ast.FuncLit`. Свободные переменные — через `types.Info.Uses`:
   идентификаторы, объявленные вне литерала и не являющиеся пакетами и не `s`.
   Их типы известны из `types.Info` — они становятся дополнительными параметрами
   метода, а в CUE — дополнительными элементами `args`. Записать метод в
   `internal/service/<service>_<method>.go` (несколько литералов одного метода — в
   один файл). Имя метода — по `output` шага, если он есть (`getTender_products`),
   иначе `<method>_<порядковый номер>`; при коллизии с существующим именем —
   ошибка миграции, не автопереименование.
   Заменить в CUE `func: """…"""` на `func: "s.<имя>"`, дополнить `args`.
4. Блоки `impls: go: code` (27): тело метода целиком → `func (s *XImpl) <method>Impl(ctx, req) (resp, error)`,
   в CUE `code: "return s.<method>Impl(ctx, req)"`. Здесь же **сначала** исправь
   `ReplaceAll("l.", "slog.")` на замену только целого `log.` (`\blog\.`) — иначе
   миграция унесёт баг в рукописный код.
5. После каждого шага: `ang build`, `go build ./...`, `go test ./...`,
   `ang build --check` (идемпотентность), `ang vet logic --types`.

**Что не делать.** Не мигрировать «по тексту CUE» (см. выше). Не переносить всё
одним коммитом: сервис за сервисом, каждый — отдельный проверяемый коммит в
dealingi-back. Не трогать 3 определения, которые собираются конкатенацией
`""" + #Block + """` (`#EnsureDemoGuestApplicationFunc`, `impl_calendar.cue`,
`impl_demo_guests.cue`) — только отчёт. Не менять `funcRef`-механизм и его тесты —
он остаётся для проектов, где им пользуются.

**Приёмка.**
- Тест ANG: проект из шаблона `saas` + один `logic.Call` с литералом → `ang migrate
  go-blocks` → в `internal/service/` появился рукописный файл с методом, CUE
  содержит `func: "s.…"`, `ang build --check` чист, `go build` зелёный, второй
  запуск миграции ничего не делает.
- На dealingi-back (в копии): после миграции одного сервиса `--dry-run --diff`
  показывает в файлах его методов **только** замену литерала вызовом (и строки
  провенанса); `go test ./...` и e2e зелёные; `grep -c '\\"' cue/api/impl_<svc>*.cue`
  уменьшился до нуля для мигрированных блоков.
- Критерий «тащиться»: правка в `internal/service/tender_products.go` → gopls
  подсвечивает ошибку типа на месте, без запуска ANG.

**Решение пользователя.** Правило проекта «никогда не редактировать `internal/`»
становится «никогда не редактировать `*.gen.go`». Это надо записать в AGENTS.md
dealingi-back до первого мигрированного сервиса.

## Что нельзя менять ни в одном из пунктов

- **Именование в схеме** (`countrys`, `companys`, `b2bsharelinks` и т. п.). Это
  таблицы в боевой базе; изменение требует миграций данных. Не трогать.
- **Форму генерируемого кода и контракт API.** Пока `ang.lock` эталонного проекта
  указывает на старый коммит, джоба `generated-output` сравнивает с ним. Если твоё
  изменение по необходимости меняет выход (например, новая секция в
  `ang-manifest.json`), это должен быть отдельный, объяснённый коммит; проект
  обновит `ang.lock` осознанно.
- **`ensureSDKTarget` и его тесты.**
- Не переписывай `build_transaction.go` «с нуля красиво» — меняй модель владения
  (P0.1), сохраняя rename-атомарность и откат.

## Как проверять любой пункт на эталонном проекте

```bash
cd ~/Desktop/work/ang && git checkout -b <ветка> && go test ./cmd/ang/... ./compiler/...
cd ~/Desktop/work/deal/dealingi-back
git status --short            # должно быть чисто до начала

                                            # на время проверки временно поставь commit= в ang.lock
                                            # на HEAD своей ветки, НЕ коммить это

make generate && git status --short         # второй раз: пусто

```

Если после твоих изменений `make generate` меняет что-то в `internal/`, `sdk/` или
`api/`, чего ты не ожидал, — это регрессия, а не «побочный эффект». Остановись и
разберись, прежде чем идти дальше.

## Критерий готовности всего плана

Агент, работающий в `dealingi-back`, может: править `impl_*.cue`, за секунды
получить ошибки типов с координатами в CUE (`P3.2`), увидеть дифф будущего кода без
записи (`P2.1`), собрать инкрементально (`P2.2`) — и при этом ни один его файл,
записанный во время сборки, не пропадёт (`P0.1`), фронт не будет удалён (`P0.2`),
а чужой бинарник не сгенерирует другой контракт (`P0.3`). Повторная сборка
даёт ноль диффа, и это проверяет `--check` (`P1`).
